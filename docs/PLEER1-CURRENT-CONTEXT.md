# Pleer1 — актуальный контекст проекта для компаньона

Дата актуализации: 2026-11-18

Этот документ дополняет `AGENTS.md` и `docs/YOUTUBE-SEARCH-DIAGNOSTICS.md`. При конфликте правил безопасности из `AGENTS.md` имеют приоритет.

## 1. Роль компаньона сейчас

Компаньон — независимый read-only инженерный помощник. Он должен сохранять контекст проекта, проверять доказательства, помогать планировать проверки и находить пробелы в данных. Он не должен заново придумывать уже согласованное решение, выдавать общие гипотезы за диагностику или заявлять, что проверил исходный код, которого нет в его рабочем репозитории.

Текущая задача Pleer1 — в первую очередь **валидация уже подготовленной версии**, а не повторный поиск причины YouTube Search:

1. Изолированная iOS-сборка и тесты интерфейса в симуляторе.
2. Проверка собранной версии пользователем на физическом iPhone.
3. Техническая оптимизация после подтверждённой проверки.
4. Обновление UI.
5. Интеграция проверенных изменений в основной Pleer1.
6. Регрессионная проверка и финальная сборка.

Не менять этот порядок без нового прямого решения пользователя. Не предлагать менять UI до завершения первых двух этапов.

## 4. Поиск: согласованное ожидаемое поведение

- Обычный запрос (например, `Concrete`) должен находить отдельные видео-треки, а не только плейлисты или Mix.
- Явный запрос коллекции (например, `crystal castles playlist`) должен находить коллекции.
- Тип результата определяется структурой renderer/типизированными данными и ID, а не словами в заголовке.
- Проверять цепочку отдельно: HTTP → renderer-кандидаты → parser → фильтры → итоговый список UI → выбранный пользователем объект.
- Весь анализ одного поиска коррелировать по одному `searchID`.

## 6. Какой результат требуется от компаньона

При каждом анализе:

1. Сначала перечислить доступные ему файлы и источники данных. Явно указать, что исходников Pleer1 в этом репозитории нет.
2. Отделить подтверждённые факты от сведений из проектного журнала и от гипотез.
3. Не повторять диагностику Build #14 как будто это новые данные.
4. Не объявлять исправление, сборку, тест или симулятор успешными без соответствующего артефакта/лога.
5. Если запрос касается текущего этапа, отвечать в контексте дорожной карты: что уже подтверждено, что ожидает запуска, какой один следующий шаг.
6. Если для вывода не хватает данных, назвать конкретный файл/лог/артефакт и ровно какие поля нужны. Не запрашивать весь проект и не предлагать переносить исходники в публичный репозиторий.
7. Не менять файлы и не запускать команды: текущий агент остаётся read-only.

## 7. Обязательный формат краткого статуса

- **Подтверждено:** только факты с источником.
- **Не подтверждено:** что нельзя утверждать.
- **Ограничение контекста:** какие источники отсутствуют.
- **Следующий шаг:** одно безопасное действие, соответствующее текущей дорожной карте.
